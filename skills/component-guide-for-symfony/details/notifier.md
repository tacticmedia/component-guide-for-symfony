# Notifier (`symfony/notifier`): details

**Applies to:** Symfony 8.1

## Key features and concepts

- **Channels**: A notification uses one or more channels: `sms`, `chat`, `email`, `browser`, `push` and `desktop`. The `sms`, `push` and `desktop` channels use the texter transports, and the `chat` channel uses the chatter transports. The `email` channel uses Mailer. The `desktop` channel shows a notification on the host that runs the PHP code, not in the browser of the user. The `browser` channel adds a flash message to the session, and it does nothing when no request exists. Entry point: `Symfony\Component\Notifier\Channel\ChannelInterface`.
- **Notifications and recipients**: `NotifierInterface::send($notification, ...$recipients)` sends a `Notification` to each recipient on each channel of the notification. A `Recipient` holds an email address, a phone number, or both. The `sms` channel throws an `InvalidArgumentException` for a recipient without a phone number. The `email` channel does the same for a recipient without an email address. Write the phone number with the international code and no spaces, for example `+3312345678`. If you give no recipient, the notifier uses `NoRecipient`. For the `sms` and `email` channels, `send()` then throws a `LogicException`. Entry points: `Symfony\Component\Notifier\NotifierInterface`, `Symfony\Component\Notifier\Notification\Notification`, `Symfony\Component\Notifier\Recipient\Recipient`.
- **Texter and chatter**: `TexterInterface::send()` sends an `SmsMessage`, a `PushMessage` or a `DesktopMessage` without a `Notification`. `ChatterInterface::send()` sends a `ChatMessage`. Without a message bus, `send()` returns a `SentMessage`, and its `getMessageId()` gives the ID from the provider. If the application uses Messenger and `message_bus` is not `false`, `send()` dispatches the message on the bus and returns `null`. If `texter_transports` or `chatter_transports` is empty, the bundle removes the `texter` or `chatter` service. Entry points: `Symfony\Component\Notifier\TexterInterface`, `Symfony\Component\Notifier\ChatterInterface`.
- **DSN transports**: A DSN string configures each provider transport, for example `twilio://SID:TOKEN@default?from=FROM`. Put the SMS, push and desktop DSNs in `texter_transports`. Put the chat DSNs in `chatter_transports`. The key of each entry is the transport name. The `transport()` method of a message (`setTransport()` on `DesktopMessage`) selects one transport by its name. Without it, the first transport that supports the message sends it. If a DSN contains a reserved URI character, encode the character, for example with `urlencode()`. Entry points: `framework.notifier.texter_transports`, `framework.notifier.chatter_transports`, `Symfony\Component\Notifier\Transport::fromDsn()` for standalone use.
- **Bridges**: Each provider is a separate package, for example `symfony/twilio-notifier`. Notifier has 82 bridges: 53 for SMS, 21 for chat, 8 for push and 1 for desktop. AmazonSns supports SMS and chat, so it counts twice. If you install a bridge package, FrameworkBundle registers its transport factory. The tables on the Notifier docs page give the package and the DSN of each bridge. The SMS table also shows the webhook support. The tables do not list ClickSend, Sevenio, Smsmode and Termii. They list Sendinblue, which has no bridge. Use `symfony/brevo-notifier` instead. If the bridge for a DSN is missing, the exception message gives the `composer require` command. In FrameworkBundle, the PagerDuty factory has only the chatter tag, so a PagerDuty DSN in `texter_transports` fails. Its transport sends only a `PushMessage`, so PagerDuty works only through `ChatterInterface` without a message bus. Entry points: the `symfony/<provider>-notifier` packages; the bridge tables at https://symfony.com/doc/current/notifier.html.
- **Failover and round-robin**: If a DSN value joins several DSNs with ` || `, the next transport sends the message when a transport fails. If the value joins the DSNs with ` && `, each message goes to the next transport in turn (round-robin). Put a space on each side of the operator. Only a `TransportExceptionInterface` error moves the message to the next transport. The failover and round-robin transports skip a failed transport for 60 seconds. Entry point: a DSN value such as `'%env(SLACK_DSN)% || %env(TELEGRAM_DSN)%'`.
- **Channel policy**: If a notification has no channels, the notifier takes the channels from `channel_policy` for the importance of the notification. The importance levels are `urgent`, `high`, `medium` and `low`, and the default level is `high`. A channel name such as `chat/slack` selects one transport of the channel. If the policy does not define the importance, `send()` throws an `InvalidArgumentException`. The Flex recipe sets `['email']` for each level. Entry points: `framework.notifier.channel_policy`, `Notification::importance()`.
- **Custom messages per channel**: A notification class can implement `SmsNotificationInterface`, `ChatNotificationInterface`, `EmailNotificationInterface`, `PushNotificationInterface` or `DesktopNotificationInterface`. Its `as*Message()` method builds the message for one channel and transport. If the method returns `null`, the channel builds the default message. To select the channels per recipient, override `Notification::getChannels()`. A message takes provider options as a `MessageOptionsInterface` object, for example `SlackOptions` or `TelegramOptions`. Entry point: `Symfony\Component\Notifier\Notification\ChatNotificationInterface::asChatMessage()`.
- **Email channel**: The `email` channel sends the notification through Mailer. If the application has `symfony/twig-bridge`, the channel sends a `NotificationEmail`, which needs `twig/cssinliner-extra` and `twig/inky-extra`. Without the Twig bridge, the channel sends a plain text `Email`. If the email has no `From` address, the channel uses `framework.mailer.envelope.sender`. If both are missing, it throws a `LogicException`. If the application does not enable Mailer, the bundle removes the `email` channel. Entry points: `Symfony\Bridge\Twig\Mime\NotificationEmail`, `EmailNotificationInterface::asEmailMessage()`.
- **Browser channel**: The `browser` channel adds the subject and the emoji of the notification as a flash message. The default flash type is `notification` for all importance levels. To get the Bootstrap types `danger`, `warning`, `info` and `success`, set the class of the `notifier.flash_message_importance_mapper` service to `BootstrapFlashMessageImportanceMapper`. Entry point: `Symfony\Component\Notifier\FlashMessage\FlashMessageImportanceMapperInterface`.
- **Messenger**: If the application uses Messenger, the channels, the texter and the chatter dispatch each message on `messenger.default_bus` or on the `message_bus` service. The bus handles a message synchronously unless `framework.messenger.routing` sends its class to an async transport. The classes are `SmsMessage`, `ChatMessage`, `PushMessage`, `DesktopMessage` and, for the `email` channel, `SendEmailMessage`. If the message of one channel fails on an async transport, Messenger retries only that message. If the application uses Messenger, do not set `message_bus: false`. The bundle then gives the channels no transport and no bus, so each channel throws a `LogicException` when the notifier uses it. Only the texter and the chatter then send directly. Entry point: `framework.notifier.message_bus`.
- **Admin alerts**: `admin_recipients` lists the administrators, and each entry takes an `email` key and an optional `phone` key. The Flex recipe adds the placeholder `admin@example.com`. Replace it with a real address. With Messenger and `notification_on_failed_messages: true`, the notifier alerts these recipients when a message fails for the last time. If a MonologBundle handler uses the `notifier.monolog_handler` service (`NotifierHandler` from `symfony/monolog-bridge`), the service alerts them about log records at level `error` or higher. These notifications have no channels. Define `channel_policy` for their importance levels: `high` for a failed message and for `error`, `urgent` for `critical` or higher. If the policy uses the `sms` channel, set `phone` for each administrator. Entry points: `framework.notifier.admin_recipients`, `framework.notifier.notification_on_failed_messages`, `notifier.monolog_handler`.
- **Events**: A transport dispatches `MessageEvent` before it sends a message. It dispatches `SentMessageEvent` after it sends the message, and `FailedMessageEvent` when an error occurs. Use these events to log the messages, to read the provider message ID or to react to an error. Entry points: `Symfony\Component\Notifier\Event\MessageEvent`, `Symfony\Component\Notifier\Event\SentMessageEvent`, `Symfony\Component\Notifier\Event\FailedMessageEvent`.
- **Delivery webhooks**: If you enable the Webhook component and install the bridge, the services `notifier.webhook.request_parser.lox24`, `.smsbox`, `.sweego`, `.twilio` and `.vonage` parse the SMS delivery callbacks. For a delivery report, each parser returns an `SmsEvent` with the name `delivered` or `failed`. For an intermediate status, the Twilio, Vonage and LOX24 parsers return `null`, and the controller answers with a 406. The Smsbox parser throws a `TypeError` for the codes `-1`, `9` and `10`. Add a route in `framework.webhook.routing` with the parser service and the provider secret. Consume the events in a class that implements `Symfony\Component\RemoteEvent\Consumer\ConsumerInterface` and has `#[AsRemoteEventConsumer('<route name>')]`. Always set the secret. The Twilio, Sweego and Vonage parsers reject an empty secret, and the LOX24 parser then skips its token check. Entry points: `framework.webhook.routing`, `Symfony\Component\RemoteEvent\Event\Sms\SmsEvent`.
- **Development and tests**: To send no notifications in the `dev` or `test` environment, set the DSNs to `null://null`. The DSNs `fakesms+logger://default` and `fakechat+logger://default` write the messages to the log. The DSN `fakesms+email://default?to=TO&from=FROM` sends them as emails. `NotificationAssertionsTrait` in `KernelTestCase` checks the sent and queued messages. With a message bus, only the texter and the chatter dispatch a queued `MessageEvent`. A channel dispatches its message to the bus without this event, so `assertQueuedNotificationCount()` does not count it. Entry points: `when@dev`, `symfony/fake-sms-notifier`, `symfony/fake-chat-notifier`, `Symfony\Bundle\FrameworkBundle\Test\NotificationAssertionsTrait`.

## Entry points

- `Symfony\Component\Notifier\NotifierInterface` (service `notifier`): sends a `Notification` on its channels.
- `Symfony\Component\Notifier\TexterInterface` (service `texter`): sends an `SmsMessage`, a `PushMessage` or a `DesktopMessage`. It exists only if `texter_transports` is not empty.
- `Symfony\Component\Notifier\ChatterInterface` (service `chatter`): sends a `ChatMessage`. It exists only if `chatter_transports` is not empty.
- `Symfony\Component\Notifier\Notification\Notification`, `Symfony\Component\Notifier\Recipient\Recipient`, `Symfony\Component\Notifier\Recipient\NoRecipient`.
- Messages: `Symfony\Component\Notifier\Message\SmsMessage`, `ChatMessage`, `PushMessage`, `DesktopMessage`, `EmailMessage`, `SentMessage`.
- Per-channel messages: `Symfony\Component\Notifier\Notification\SmsNotificationInterface`, `ChatNotificationInterface`, `EmailNotificationInterface`, `PushNotificationInterface`, `DesktopNotificationInterface`.
- Config: `framework.notifier` with the keys `enabled`, `chatter_transports`, `texter_transports`, `channel_policy`, `admin_recipients` (`email`, `phone`), `notification_on_failed_messages` and `message_bus`.
- Events: `Symfony\Component\Notifier\Event\MessageEvent`, `SentMessageEvent`, `FailedMessageEvent`.
- Service IDs: `notifier.flash_message_importance_mapper`, `notifier.monolog_handler`, `notifier.failed_message_listener`, `notifier.webhook.request_parser.lox24`, `notifier.webhook.request_parser.smsbox`, `notifier.webhook.request_parser.sweego`, `notifier.webhook.request_parser.twilio`, `notifier.webhook.request_parser.vonage`.
- Custom provider: extend `Symfony\Component\Notifier\Transport\AbstractTransport` and `Symfony\Component\Notifier\Transport\AbstractTransportFactory`. Autoconfiguration adds the `chatter.transport_factory` and `texter.transport_factory` tags to the factory.
- Custom channel: implement `Symfony\Component\Notifier\Channel\ChannelInterface`. Tag the service with `notifier.channel` and a `channel` attribute. Autoconfiguration does not add this tag.
- Without FrameworkBundle: `Symfony\Component\Notifier\Transport::fromDsn()`.
- Tests: `Symfony\Bundle\FrameworkBundle\Test\NotificationAssertionsTrait` (used by `KernelTestCase` and `WebTestCase`) with `assertNotificationCount()`, `assertQueuedNotificationCount()`, `assertNotificationIsQueued()`, `assertNotificationIsNotQueued()`, `assertNotificationSubjectContains()`, `assertNotificationSubjectNotContains()`, `assertNotificationTransportIsEqual()`, `assertNotificationTransportIsNotEqual()`, `getNotifierEvents()`, `getNotifierEvent()`, `getNotifierMessages()` and `getNotifierMessage()`.
- Bridge tests: `Symfony\Component\Notifier\Test\TransportTestCase`, `Symfony\Component\Notifier\Test\AbstractTransportFactoryTestCase`.
- The package has no console commands, no Twig functions and no PHP attributes.

## Symbiotic packages

- [Mailer](../packages/mailer.md): The `email` channel sends notifications through Mailer and needs `framework.mailer`. For a transactional email without channels, use Mailer directly.
- [Messenger](../packages/messenger.md): If the application uses Messenger, the channels, the texter and the chatter dispatch their messages on the bus, and routing makes the delivery asynchronous.
- [Twig Bridge](../packages/twig-bridge.md): `NotificationEmail` gives the `email` channel an HTML template with `content()`, `markdown()`, `action()` and `theme()`.
- [TwigBundle](../packages/twig-bundle.md): TwigBundle registers the `@email` template namespace that holds the notification email templates.
- [Webhook](../packages/webhook.md): The Webhook component receives the SMS delivery callbacks of five bridges. To send signed webhooks to other systems, use Webhook, not Notifier.
- [RemoteEvent](../packages/remote-event.md): The notifier webhook parsers return `SmsEvent` objects, and an `#[AsRemoteEventConsumer]` class consumes them.
- [Security](../packages/security-bundle.md): `LoginLinkNotification` from `symfony/security-http` sends a login link by email or SMS through `NotifierInterface`.
- [Monolog Bridge](../packages/monolog-bridge.md): `NotifierHandler` (service `notifier.monolog_handler`) turns log records at level `error` or higher into notifications to the admin recipients.
- [MonologBundle](../packages/monolog-bundle.md): A handler with `type: service` and `id: notifier.monolog_handler` connects the log channels to the notifier.
- [Mercure](../packages/mercure.md): The `symfony/mercure-notifier` chat bridge publishes messages to a Mercure hub and needs MercureBundle. The bridge accepts `symfony/mercure` only up to 0.8 (`^0.5.2|^0.6|^0.7|^0.8`). So with MercureBundle 0.6 (`^0.8|^0.9`), Composer installs `symfony/mercure` 0.8, not 0.9.
- [Symfony UX Notify](../packages/ux-notify.md): UX Notify shows the Mercure chat messages as native browser notifications through `stream_notifications()`. The `browser` channel only adds flash messages. UX Notify requires MercureBundle `^0.3.4|^0.4.1`, so it does not install with MercureBundle 0.5 or 0.6.
- [HttpClient](../packages/http-client.md): 81 of the 82 bridges require HttpClient to call the provider APIs; Mercure is the exception.
- [HttpFoundation](../packages/http-foundation.md): The `browser` channel writes flash messages to the session of the current request.
- [FrameworkBundle](../packages/framework-bundle.md): The `framework.notifier` configuration creates the `notifier`, `texter` and `chatter` services and registers the installed bridges.
- [FrameworkBundle test tools](../packages/framework-bundle-testing.md): `KernelTestCase` includes `NotificationAssertionsTrait` for the notification assertions.
- [WebProfilerBundle](../packages/web-profiler-bundle.md): The profiler shows the sent and queued notification messages of a request, grouped by transport.
- [Emoji](../packages/emoji.md): often confused by name; `Notification::emoji()` only stores the icon string of a notification and does not use Emoji.

## Changed in 8.0/8.1

- `symfony/sms77-notifier` -> `symfony/sevenio-notifier`. Symfony 7.3 deprecates the Sms77 bridge and names the Seven.io bridge as its replacement. Symfony 8.0 removes the Sms77 bridge. Packagist marks the package as abandoned (last version v7.4.17). Change the DSN `sms77://API_KEY@default?from=FROM` to `sevenio://API_KEY@default?from=FROM`.
- `TransportFactoryTestCase` -> `AbstractTransportFactoryTestCase`, with `IncompleteDsnTestTrait` or `MissingRequiredOptionTestTrait` for the incomplete-DSN and missing-option tests (removed in 8.0).
- Fluent config builders such as `$framework->notifier()->chatterTransport('slack', ...)` -> a PHP array, for example `App::config(['framework' => ['notifier' => [...]]])`. Symfony 8.0 removes the config builder classes such as `Symfony\Config\FrameworkConfig` and their fluent methods. The framework configuration reference shows them for the notifier keys.
- New in 8.1: the Prelude SMS bridge, `symfony/prelude-notifier`, with the DSN `prelude://API_KEY@default?sender=FROM`.
- New in 8.1: the Telegram DSN option `sslmode=disable` sends the requests over HTTP, for example to a local Telegram API server.
- Webhook security: the LOX24 parser checks the `X-LOX24-Token` header and the Twilio parser checks the HMAC signature since 8.0.12 and 8.1.0 (CVE-2026-45754, CVE-2026-47212). Since 8.1.7, the Twilio and Sweego parsers reject an empty secret. Set `secret` on each notifier webhook route.
